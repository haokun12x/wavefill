# Wavefill 技术报告：RTX 5090 上大模型推理的性能边界与超长上下文 prefill 优化

> 被测系统：[NInfer](https://github.com/Neroued/ninfer) `9e163eee`（C++/CUDA 推理引擎）+ Wavefill 的三个提交
> 模型：Qwen3.8-27B（FP8/NVFP4 混合权重），单卡 RTX 5090
> 日期：2026-09 至 2026-10。除特别注明为“估算”的数字，全部是本机实测，原始数据在 [`results/`](results/)。
> 开发过程借助了 AI 编程助手（Claude Code）。

## 摘要

这份报告回答两个问题。

**第一，在单请求 decode 这类带宽受限的场景里，算子层面还能优化多少？** 答案是“几乎没有了”。实测这块 RTX 5090 的纯读带宽上限是 1.70 TB/s（名义值的 95%，TMA 和普通向量加载两条完全不同的路径都收敛到这个值）。NInfer 的 decode 已经达到这个上限的 87%，GPU 忙碌率 98.6%。剩下 13% 里，现实可回收的是 4–8%。我做了其中最大的一项（NVFP4 下投影 GEMV），整机 decode 快 1.25%。查下来，这个缺口的根因是全展开代码的**冷取指**，不是访存效率。想再往上走，只能“移动上限”（每 token 读更少字节，或者每读一遍权重产出更多 token），不能靠“逼近上限”。

**第二，在 agent 这类超长上下文场景里，瓶颈在哪里，能拿回多少？** 这里的情况正好相反：prefill 注意力是计算受限的，但只用到张量核心峰值的 60%。损失可以干净地拆成两个乘性因子：

- **波次量化**：一个 SM 只能放 1 个 CTA，tile 数又不是 SM 数的整数倍，所以总有一部分 SM 空转。
- **累加精度带来的吞吐减半**：P·V 用的是 FP32 累加，而这块卡上 FP32 累加的吞吐只有 FP16 累加的一半。

两个因子各用一个改动解决：

- **cluster split-KV**：用线程块簇切分 key 范围，经分布式共享内存合并，不需要全局工作区；
- **可证明不溢出的 FP16 累加 P·V**：P 按块内局部最大值取值再乘 2⁻⁶，块结束时折回 FP32 累加器。

结果：

| 场景 | 改前 → 改后 | 提速 |
|---|---|---:|
| prefill 注意力内核，64k 上下文，1024 token 分块（BF16 / INT8 / FP8 KV） | 11.01 → 7.85 ms 等 | **1.40× / 1.29× / 1.35×** |
| agent 增量 prefill 的注意力内核，64k 历史，追加 128 / 256 / 512 token | 3.63 → 1.06 ms 等 | **3.42× / 1.72× / 1.82×** |
| 整机冷启动 prefill，32k / 64k / 128k prompt | 4.25 → 4.01 s 等 | **1.06× / 1.12× / 1.18×** |
| 整机 agent 单轮，64k 历史上追加 128 / 512 / 4096 token，到首 token | 102 → 65 ms 等 | **1.56× / 1.30× / 1.20×** |

整机提速低于内核提速，原因已经定量查清：长 prefill 时整卡持续顶在 600 W 功耗墙。新内核让张量核心更忙，SM 频率中位数从 2745 MHz 降到 2595 MHz（−5.5%）。1.40 × 2595/2745 = 1.32，正好等于引擎里实测的注意力提速。

报告的组织方式是：先测清硬件上限，再建立性能模型，用模型定位损失，最后用模型预测、用实测验证。几个模型都只用 1–2 个参数，就把几十个测量点解释到 1–3% 以内。

### 1.1 硬件

| 项目 | 值 | 来源 |
|---|---|---|
| GPU | GeForce RTX 5090（GB202），计算能力 12.0，编译目标 `sm_120a` | `cudaGetDeviceProperties` |
| SM | 170 个，分布在 11 个 GPC（8 个 16-SM GPC + 3 个 14-SM GPC，推断过程见 §5.3） | 实测簇驻留能力反推 |
| 每 SM 资源 | 4 个调度分区（SMSP），64K 个 32 位寄存器，最多 1536 线程，共享内存 100 KB（单 CTA 最多 99 KB） | `cudaGetDeviceProperties` |
| L2 | 96 MB | 同上 |
| 显存 | 32 GB GDDR7，512 位总线，名义 1792 GB/s；实测显存频率 13.8 GHz（标称 14.0），理论约 1766 GB/s | `nvidia-smi` |
| 功耗墙 | 600 W | `nvidia-smi` |
| SM 频率 | 空载 boost 约 2.87 GHz；长时间满载受功耗墙约束（§8.5） | 实测采样 |

**体系结构上的关键约束**：sm_120 没有 Hopper 的 `wgmma`，也没有数据中心 Blackwell 的 `tcgen05`/TMEM，张量核心只能通过 warp 级的 `mma.sync` 使用（另有块缩放的 FP4/FP6/FP8 变体）。TMA、线程块簇（cluster）和分布式共享内存（DSMEM）是有的。因此在这块卡上，FlashAttention-3 依赖的“异步 warpgroup MMA + 寄存器释放”那套机制不能直接搬过来，所有 MMA 都要占用发射它的 warp 的寄存器和发射槽。

### 1.2 先测上限

不知道上限，就无法判断一个内核“好不好”。所以先用自写的微基准测了两类上限。

**张量核心峰值**（[`results/mma_peak.txt`](results/mma_peak.txt)，170 SM × 4 CTA × 8 条独立累加链，boost 频率）：

| `mma.sync` 形状 | 实测 | 每 SMSP 每周期 | 一条 MMA 的发射间隔 |
|---|---:|---:|---:|
| BF16 / FP16 → FP32 累加（m16n8k16） | 250.8 TFLOP/s | 128 FLOP | 32 周期 |
| FP16 → **FP16 累加**（m16n8k16） | **500.7** | 256 | 16 |
| INT8 → INT32（m16n8k32） | 997.2 TOP/s | 512 | 16 |
| E4M3 → FP32 / FP16 累加（m16n8k32） | 499.2 / 997.6 | 256 / 512 | 32 / 16 |

“每 SMSP 每周期”按 250.8×10¹² / (170 × 4 × 2.87×10⁹) ≈ 128.5 推算。一个重要事实是：**这块卡上 FP16 输入、FP32 累加的吞吐恰好是 FP16 累加的一半**，这与 GeForce 产品线历来的分级一致。§6 的优化就建立在这一点上。

**显存纯读上限**（4 GiB 工作集，L2 的 42 倍；[`tools/wavefill/bw_variants.cu`](../../tools/wavefill/bw_variants.cu)，数据 [`results/bandwidth_ceiling.txt`](results/bandwidth_ceiling.txt)）：

| 读法 | 最好 GB/s | 占名义 1792 |
|---|---:|---:|
| `ld.global.nc.v4`，grid-stride，170 CTA × 256 线程，不展开 | 1547 | 86.3% |
| 同上，展开 4 / 8 | 1701 / 1702 | 95.0% |
| 同上，340 CTA，不展开 | 1695 | 94.6% |
| TMA 一维 bulk 拷贝（`cp.async.bulk`，3–6 级流水） | **1705** | 95.1% |
| 每个 CTA 读自己的一段连续区域（GEMV 行切分的样子） | 1663 | 92.8% |
| 加 `L1::no_allocate.L2::256B` 提示 | 1456 | 81.3% |

两条完全不同的数据通路（LSU 向量加载和 TMA 异步拷贝）都停在 1702–1705 GB/s，说明这是 **DRAM 本身的上限**，不是某种指令写法的上限。剩下的 5% 是 GDDR7 的协议开销（刷新、行激活和预充电、读写换向），软件拿不回来。

前三行可以用 **Little 定律**解释：带宽 = 在途字节数 / 延迟。

- 170 CTA × 256 线程 × 16 B = 680 KiB 在途，得到 1547 GB/s，反推有负载时的平均访存延迟约 450 ns。
- 在途字节翻倍（展开 4，或者 CTA 数翻倍），带宽就饱和在约 1.70 TB/s。也就是说，全卡需要约 1 MiB 以上的在途读请求（每个 SM 约 6–8 KiB）才能喂饱 DRAM。

后面判断“预取能不能帮忙”，都以这个数为准。

### 1.3 模型与引擎

**Qwen3.8-27B 是混合架构**。64 层里：

- 48 层是 Gated DeltaNet（线性注意力，状态大小固定）；
- 16 层是标准全注意力：GQA，24 个查询头、4 个 KV 头，head dim D = 256。

权重是混合精度：全部注意力/GDN 投影、lm_head 和第 56–63 层的 MLP 是 FP8（逐行缩放）；第 0–55 层的 MLP 是 NVFP4（16 元素块缩放）。每生成一个 token 要读 19.05 GB 权重，外加约 0.30 GB 的 GDN 状态。

**NInfer 引擎**的几个相关特性：

- decode 整步用 CUDA Graph 回放；
- prefill 按 1024 token 分块；
- KV 缓存分页（每页 64 token），支持 BF16 / INT8 / FP8 等格式；
- 前缀缓存保存“KV + GDN 递推状态”的检查点。对混合模型这是必须的：线性注意力的状态不能截断，只能在保存过的边界上恢复；
- 支持 MTP 投机解码。

### 1.4 测量方法

1. **上限先行**：所有效率都以 §1.2 实测的上限为分母，不用规格书的名义值。
2. **四层证据链**：微基准（隔离单一因素）→ 算子基准（`ninfer_*_bench`，冷 L2、CUDA Graph）→ 引擎内 nsys 轨迹（真实前后驱内核）→ 整机交替 A/B（新旧二进制交替运行以抵消漂移）。任何结论都至少要两层一致。
3. **计时分辨率**：GPU event 的粒度是 2.048 µs，所以对 50 µs 以下的内核，只相信 10% 以上的差异。
4. **长时间计算受限的测试要采样频率和功耗**（每 100 ms 采一次 `nvidia-smi`），否则测不到功耗墙（§8.5）。
5. **正确性**：
   - FP64 oracle 逐点比对；
   - 专门的数值压力测试；
   - compute-sanitizer 四个工具；
   - 全二进制 SASS 逐函数对比（确认只有目标内核变了）；
   - 能逐位一致的改动要求逐位一致。

## 2. 理论框架：每个阶段受什么限制

### 2.1 Roofline

内核的可达性能是 $P = \min(\pi,\ \beta \cdot I)$。其中 $\pi$ 是计算峰值，$\beta$ 是带宽，$I$ 是算术强度（FLOP/字节）。拐点 $I^* = \pi/\beta$。这块卡上：

| 计算类型 | $\pi$ | $I^* = \pi / 1.70\,\text{TB/s}$ |
|---|---:|---:|
| BF16，FP32 累加 | 251 TFLOP/s | 148 FLOP/B |
| FP8，FP32 累加 | 499 | 294 |
| FP16 累加 / INT8 | 501 / 997 | 295 / 587 |

### 2.2 decode：带宽受限 40–70 倍

一个 token 经过权重矩阵时，每个权重做一次乘加（2 FLOP）。

- FP8 每个权重 1 字节，$I = 2$ FLOP/B；
- NVFP4 每个权重 4 bit，另有每 16 个共用 1 字节缩放，合 4.5 bit，$I \approx 3.6$ FLOP/B。

这两个值都比拐点低 40–70 倍。所以单请求 decode 的时间下界就是“把权重和状态读一遍”的时间：

$$t_\text{token} \ \ge\ \frac{19.05 + 0.30\ \text{GB}}{1.70\ \text{TB/s}} = 11.4\ \text{ms} \quad\Rightarrow\quad \le 88\ \text{tok/s}$$

实测 77.4 tok/s（12.9 ms），约为下界的 87%。这个下界与内核写法无关，只取决于字节数和带宽。要越过它，只能：

- 每读一遍权重处理 T 个 token（投机解码、多请求并发），强度随 T 线性增长；
- 减少字节数（更激进的量化）。

开 MTP3 后单请求 decode 达到 154 tok/s，约为无投机的 2 倍，就是第一种方式。

### 2.3 prefill 注意力：计算受限，而且 DRAM 几乎是闲的

一个 T token 的分块，在上下文 C 上做一层因果注意力（$H_q$=24，$H_{kv}$=4，D=256）：

$$F = 4\,H_q\,T\,D\left(C + \tfrac{T}{2}\right), \qquad B_\text{unique} = 2\,H_{kv}\,(C+T)\,D\,b$$

其中 QK 和 PV 各占一半 FLOPs，b 是每元素字节数。按唯一字节数算的强度是

$$I = \frac{F}{B} \approx \frac{2\,(H_q/H_{kv})\,T}{b} = \frac{2 \times 6 \times 1024}{2} = 6144\ \text{FLOP/B}$$

比拐点高 40 倍，是彻底的计算受限。ncu 证实了这一点：32k/64k 上下文时 DRAM 吞吐只有 0.9–2.1%，L2 命中率 98.7%。

这个命中率本身可以预测。每个 64-key 的 K/V 块（每个 KV 头 64 KB）会被 $(H_q/H_{kv}) \times (T/64) = 6 \times 16 = 96$ 个 CTA 读取。这些 CTA 大致同步地沿 key 方向推进，所以每个块只从 DRAM 取一次，后面 95 次都命中 L2。命中率 ≈ 1 − 1/96 = 98.96%，与实测的 98.74% 吻合。

### 2.4 整段 prefill：二次项迟早占主导

N 个 token 的 prompt 分成 N/1024 块，第 c 块的上下文是 1024·c。对所有块求和：

$$t_\text{prefill}(N) \;=\; \underbrace{\alpha N}_{\text{GEMM、GDN 等}} \;+\; \underbrace{\frac{196{,}608\,N^2}{R_\text{attn}}}_{\text{16 层注意力}}$$

推导：每对 (query, key) 在 16 层里共 $4 H_q D \times 16 = 393{,}216$ FLOP，因果对数约为 $N^2/2$。$\alpha$ 是按 2048 token 实测轨迹定的：每块非注意力开销 88 ms，即 86 µs/token。$R_\text{attn}$ 是注意力内核的实际吞吐。

两项相等时有 $N^* = \alpha R_\text{attn} / 196{,}608$：

- 改前（$R_\text{attn}$ = 151 TFLOP/s）：$N^*$ ≈ **66k**。64k prompt 的 prefill 有一半时间花在 16 层注意力上，256k 时是 80%（表见 §4.2）。
- 改后（212 TFLOP/s）：$N^*$ 推迟到 93k。

用这个模型和基线 INT8 内核时间推算 260k 是 2361 tok/s，NInfer 官方公布的实测是 2203 tok/s；推算 8k 是 10.3k tok/s，本机实测 pp7680 是 10.1k。

### 2.5 agent 单轮：线性注意力层的代价与历史长度无关

agent 的一轮是：在已有的 C 个 token 历史后追加 d 个新 token（工具输出、文件内容、用户消息），prefill 这 d 个 token，然后生成一段回复。如果引擎保留了上一轮的检查点，只需算这 d 个 token：

$$t_\text{turn}(C,d) \;=\; t_\text{linear}(d) \;+\; 16\cdot t_\text{attn}(C,d), \qquad F_\text{attn} \propto d\cdot\left(C+\tfrac{d}{2}\right)$$

- **48 层 GDN** 的每 token 代价与 C 无关，因为状态大小固定。
- **GEMM 部分**在 d 较小时受“把 19 GB 权重读一遍”的约束（约 11–15 ms），也与 C 无关。
- **只有 16 层全注意力**的代价随 C 线性增长。

所以在混合架构模型上，**长历史 agent 的单轮延迟主要由 16 层注意力在“短查询 × 长 key”形状上的效率决定**（实测 64k 历史、追加 128 token 时约占单轮 prefill 的 63%，§8.4），而且历史越长占比越高。这个形状恰好是原内核最差的情况（§4.4）。

## 3. 第一部分：decode 已经贴近硬件上限

### 3.1 decode 全景

单请求、无投机 decode 的一个 token = 641 个内核、13.06 ms：

- GPU 忙碌率 98.6%，641 个内核间隙合计 183 µs，宿主侧没有气泡；
- 权重流内核占 94% 的时间。

| 权重内核族 | 相对 1.70 TB/s 的实际带宽 |
|---|---:|
| lm_head | 99.8% |
| 注意力输入投影 | 95% |
| FP8 下投影、NVFP4 gate/up + SwiGLU | 94% |
| GDN 输入投影（16384×5120） | 91% |
| FP8 MLP（T=1 走 MMA）/ 输出投影 | 89–90% |
| NVFP4 下投影（5120×17408，56 层） | **83%**（最明显的短板） |

1.71 ms 的总差距（13.1 ms 实测对 11.4 ms 下界）拆开是：

| 来源 | 时间 | 占比 |
|---|---:|---:|
| 权重内核没到上限 | 1.09 ms | 8.2% |
| 小内核（RMSNorm、conv、GDN 递推、注意力……，已扣除必要的状态读写） | 0.44 ms | 3.3% |
| 内核之间的空隙 | 0.18 ms | 1.4% |

### 3.2 案例：NVFP4 下投影 GEMV 的“83%”其实是冷取指

**现象**：真实 decode 轨迹里这个内核 35.1 µs，纯读下限 31.0 µs。

**第一个假设（错的）**：内核的访存流水不够深。我做了寄存器预取队列（深度 2–6）、每 lane 16 B 加载、各种 CTA 形状，全部持平或更慢。按 §1.2 的 Little 定律算，它的在途字节本来就够。

**关键实验**：把同一个内核放到不同的上下文里跑。

| 同一个内核 | 耗时 |
|---|---:|
| 背靠背连续跑 | 31.7 µs（下限的 97%） |
| 紧跟真实的 SwiGLU 内核（同样是大代码量） | 33.4 µs |
| 紧跟一个代码量很小的纯读内核 | 31.7 µs |
| 真实 decode | 35.1 µs |

决定耗时的是**前一个内核的代码量**，不是数据。根因是**冷取指**。这个 GEMV 把 34 个 K 相位全部展开，SASS 有 6520 条指令（102 KiB）。全展开的直线代码里，每条指令对每个 warp 只执行一次，没有时间局部性；decode 每层只调用它一次，中间还夹着十几个别的内核。所以每次启动都要从 L2/显存重新取这 102 KiB 指令。ncu 里 11% 的 warp 停顿是 `no_inst`（没有指令可发），也印证了这一点。

**改动**：给 `Nvfp4GemvSchedule` 加一个默认等于“全展开”的 `PhaseUnroll` 参数（已有实例不变），这个形状改为展开 4。代码缩到 1248 条（20 KiB），循环体被重复执行 8.5 次，第一遍之后就是热的。

| | 改前 | 改后 |
|---|---:|---:|
| 背靠背 / 紧跟 SwiGLU / 真实 decode | 31.7 / 33.4 / 35.1 µs | 31.7 / 32.2 / 32.6 µs |
| 真实 decode 中位数（nsys，7224 次） | 35.14 µs | 32.58 µs（−7.3%） |
| 整机 decode（交替 3 轮） | 76.92 tok/s | **77.88 tok/s（+1.25%）** |

预测值是 56 层 × 2.56 µs = 0.14 ms/token ≈ +1.1%，与实测吻合。

**为什么输出逐位一致**：展开只改变控制流，不改变每个累加器上 FMA 的先后顺序。浮点加法不满足结合律，所以“求和顺序不变”是逐位一致的充要条件。实测在真实 56 层权重上与旧内核 0 ulp 差异。

**方法学教训**：背靠背启动的微基准会系统性高估大代码量的内核。必须在真实前驱内核之后测，或者直接看真实轨迹。

### 3.3 其余手段为什么收益很小：负结果

| 尝试 | 结果 | 说明了什么 |
|---|---|---|
| GEMV 显式寄存器预取，深度 2–6 | 持平或更慢；寄存器超过 128 后每 SM 只放得下 3 个 CTA，T=4 的 640 个 CTA 变成两波，反而慢 20–27% | 在途字节已满足 Little 定律，再加只会挤占占用率 |
| 用 `cp.async.bulk.prefetch.L2` 提前把下一层权重拉进 L2（64 层合成链） | 持平到 −8% | 已经在带宽上限上，预取不会创造带宽，只会和当前内核抢同一条 DRAM 通道并污染 L2 |
| PDL（程序化依赖启动）+ 在等待依赖之前先发寄存器加载 | 合成链 +1.5% ~ +2.9%（[`results/pdl_chain_synthetic.txt`](results/pdl_chain_synthetic.txt)） | 能回收的只是内核边界上约 1.2 µs 的爬坡和收尾时间 |
| 和 NVIDIA cuBLASLt 比（NVFP4 5120×17408，T ≤ 64） | 0.9–1.0×，持平 | 厂商库在这个形状上也没有更好的办法 |

把各项可回收量加起来：NVFP4 下投影（已做，+1.25%）、其余权重内核从 89–91% 提到 93–94%（约 +2%）、PDL（+1.5–3%）、融合小内核（≲ +1.5%），各项有重叠，**现实范围约 +4–8%，理论天花板 +13%**。

### 3.4 小结：要移动上限，而不是逼近上限

decode 的性能由“每 token 读多少字节”和“带宽”决定，后者已经用到 87%。真正能大幅提速的手段都在改变前者，或者改变每读一遍能产出的 token 数：

- 投机解码已经带来 2 倍。
- 把 FP8 的注意力/GDN 投影换成 NVFP4 可以减少约 16.5% 的字节，但需要重新量化和质量评估。

还有一个**不同类型的上限**值得记下。开 MTP3 时 T=4，NVFP4 MLP 的两个 SIMT 内核只到带宽上限的 80–87%。ncu 显示它们是**发射受限**：每个权重约 11 条指令，发射槽利用率 45.7%。这里该做的是改用张量核心的 A16 路径，把每个权重的指令数降到 1/3–1/4，估算可让 MTP3 decode 再快约 3%。这一项尚未实施。

这也回答了“用 cuTile Rust 或 cuda-oxide 完整重写会不会更快”。不会。

- 上限由 DRAM 决定，与写内核的语言无关。
- sm_120 上没有 `wgmma`/`tcgen05`，任何 DSL 最终都生成同样的 `mma.sync`。
- 实测 cuda-oxide 生成的 FP8 `mma` 内核与 nvcc 写的同逻辑内核 SASS 指令数相同、耗时相同（都是 45.0 µs）。
- 用 `--lineinfo` 构建时，它的代码生成还会显著改变（同一内核慢 4.96×），剖析信息反而更难用。

正确的做法是逐个替换有缺口的内核，而不是重构引擎。

## 4. 第二部分：agent 超长上下文场景的 prefill

### 4.1 agent 负载的特征

以编码 agent 为例，一次任务会循环几十到上百步。每一步：

1. 把工具结果（文件内容、命令输出、diff，通常 100–4000 token）追加到对话末尾；
2. prefill 新增部分；
3. 生成一个较短的工具调用；
4. 执行工具，回到第 1 步。

这个负载有四个特点：

- **上下文单调增长**：系统提示 + 工具定义通常就有 10–30k token，几十步之后到 64k–128k 是常态。
- **步与步严格串行**：下一步依赖上一步的输出，所以每一步的“到首 token 时间”直接累加成任务时长。
- **两种 prefill 并存**：
  - 冷启动（首轮、缓存未命中、上下文压缩之后）要 prefill 整段长 prompt，代价是 N 的二次函数；
  - 热增量是在长度 C 的历史上追加 d 个 token，注意力代价 ∝ C·d。
- **混合架构让注意力成为唯一随历史增长的部分**（§2.5）。

我用一个 agent 多轮基准验证了 NInfer 的前缀复用确实只算增量：每轮把上一轮的 prompt 加输出原样带上，再追加 d 个新 token，引擎报告的 `reused_prompt_tokens` 恰好等于历史长度。

### 4.2 注意力在 prefill 里的占比

| prompt 长度 | 8k | 32k | 64k | 128k | 192k | 256k |
|---|---:|---:|---:|---:|---:|---:|
| 16 层注意力占 prefill 时间（BF16 KV，改前） | 11% | 33% | 50% | 67% | 75% | 80% |
| 改后 | 9% | 27% | 42% | 59% | 68% | 74% |

（由 §2.4 的模型配合实测的注意力内核时间算出；64k 一点有 nsys 实测：5.68 s / 11.50 s = 49%。）

### 4.3 原内核的资源结构

NInfer 的因果 prompt 注意力内核（BF16 KV 版本）是 FlashAttention-2 式的：一个 CTA 负责一个“64 行查询块 × 一个查询头”，沿 key 方向每次处理 64 个 key，做在线 softmax。D = 256 让它的资源占用很紧：

| 资源 | 用量 | 计算 |
|---|---:|---|
| 共享内存：Q / K / V 各一块 | 96 KB（上限 99 KB） | 64 × 256 × 2 B × 3 |
| 寄存器：输出累加器 O | 128 个/线程 | 64 × 256 × 4 B ÷ 128 线程 |
| 寄存器：总计 | 254 个/线程（上限 255） | ncu |
| 每 SM 驻留 | **1 个 CTA = 4 个 warp = 每个调度分区 1 个 warp** | 受共享内存限制 |

ncu（32k 上下文，[`results/ncu_prompt_attention.txt`](results/ncu_prompt_attention.txt)）显示，每个调度器平均只有 0.12–0.17 个可发射 warp，实测占用率 8.3%。

后果是：**一个调度分区上只有一个 warp，任何非 MMA 指令（softmax 的 exp、max、sum，类型转换，等待 K/V 到达）都无法被别的 warp 掩盖**，只能靠单个 warp 内部的指令级并行。在 D=128 的常见配置里，累加器和暂存区都只有一半大，通常可以每 SM 放 2 个 CTA 或 8 个 warp。D=256 把这条路堵死了，这是下面所有分析的出发点。

### 4.4 损失模型：波次量化 × 单 SM 效率

一个 T token 的分块有 $U = \lceil T/64 \rceil \times 24$ 个 tile。每个 tile 独占一个 SM，170 个 SM 要跑 $\lceil U/170 \rceil$ 波，波次效率是

$$\eta(T) = \frac{U}{170\,\lceil U/170\rceil}$$

在上下文远大于 T 时，各 tile 的工作量几乎相同（64k 时最长和最短只差 1.4%），所以内核吞吐应当等于 $\eta(T)$ 乘一个与 T 无关的单 SM 效率 $R$。用 64k 上下文、不同追加长度的实测检验：

| 追加 token 数 T | tile 数 U | 波次 | $\eta$ | 实测 TFLOP/s（改前） | 实测 ÷ $\eta$ |
|---:|---:|---:|---:|---:|---:|
| 128 | 48 | 1 | 28.2% | 56.8 | 201.2 |
| 256 | 96 | 1 | 56.5% | 113.2 | 200.5 |
| 512 | 192 | 2 | 56.5% | 113.5 | 201.0 |
| 1024 | 384 | 3 | 75.3% | 151.4 | 201.1 |
| 2048 | 768 | 5 | 90.4% | 179.6 | 198.8 |
| 4096 | 1536 | 10 | 90.4% | 180.8 | 200.1 |

**6 个点只用一个参数 $R$ = 200 TFLOP/s 就解释到 ±0.7% 以内。** 于是原内核的 60% 效率（1024 token 分块时 151/251）可以精确拆成：

$$\underbrace{60\%}_{\text{实测}} \;=\; \underbrace{75.3\%}_{\text{波次效率 }\eta} \;\times\; \underbrace{80\%}_{R\,/\,\pi_\text{FP32acc} = 200/251}$$

这个分解说明了两件事：

- 原内核满载时，单 SM 已经用到 FP32 累加峰值的 80%，**在原有的 FP32 累加上限内已经没多少可挖**。所以第二个杠杆必须是**抬高上限本身**（§6），而不是继续优化流水。
- 对 agent 的短增量（T = 128–512），波次效率只有 28–56%，**大半张卡是空的**。这部分是最大的单项损失，也正是 agent 每一轮都要付的代价。

## 5. 优化一：cluster split-KV

### 5.1 数学基础：在线 softmax 是一个幺半群

对一行查询，把一段 key 集合 $K$ 上的部分结果记为三元组

$$s(K) = \big(m,\ \ell,\ \mathbf{o}\big),\quad m=\max_{j\in K} x_j,\quad \ell=\sum_{j\in K} e^{x_j-m},\quad \mathbf{o}=\sum_{j\in K} e^{x_j-m}\,\mathbf{v}_j$$

两个不相交集合的结果可以合并：

$$s_1 \oplus s_2 = \Big(M,\ \ell_1 e^{m_1-M}+\ell_2 e^{m_2-M},\ \mathbf{o}_1 e^{m_1-M}+\mathbf{o}_2 e^{m_2-M}\Big),\quad M=\max(m_1,m_2)$$

$\oplus$ 满足结合律和交换律，单位元是 $(-\infty, 0, \mathbf{0})$，最终输出是 $\mathbf{o}/\ell$。所以：

- 在精确算术下，**key 范围可以任意切分、以任意顺序合并，结果都相同**。这是 split-KV 正确性的全部依据。
- 在浮点下，不同的合并顺序会有不同的舍入。所以实现里固定按 rank 顺序归约，保证结果是确定的（同输入同输出）。

### 5.2 为什么用线程块簇，而不是 Flash-Decoding 式的全局工作区

通常的 split-KV（Flash-Decoding）把各段的 $(m, \ell, \mathbf{o})$ 写到全局内存，再启动一个合并内核。在这里它有三个代价：

1. **工作区很大**：一个 1024 token 分块、24 个头、S=2 时，FP32 的部分输出就是 2 × 1024 × 24 × 256 × 4 B = 50 MB。而 NInfer 的显存规划假定 prompt 路径的工作区为 0，引擎启动时就把显存分完了。
2. 多一次内核启动，以及一次全局内存往返。
3. 合并内核本身也有自己的波次量化问题。

线程块簇提供了另一种做法。同一个簇里的 S 个 CTA 保证被同时调度到同一个 GPC 上，彼此可以通过 DSMEM（`cluster.map_shared_rank`）直接读对方的共享内存。合并完全在片上完成：每个 tile 的合并流量只有 S × 64 × 256 × 4 B = S × 64 KB，不需要全局工作区，也不需要第二个内核。

代价是簇有驻留约束：一个簇的 S 个 CTA 必须在同一个 GPC 里同时找到 S 个空闲 SM。这正是下一节的问题。

### 5.3 从簇驻留能力反推 GPC 拓扑

用 `cudaOccupancyMaxActiveClusters` 实测“簇大小为 S 时全卡最多同时驻留多少个簇”（每 CTA 独占一个 SM；[`results/cluster_occupancy.txt`](results/cluster_occupancy.txt)）：

| S | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9–14 | 15–16 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 驻留簇数 | 170 | 85 | 52 | 41 | 30 | 22 | 22 | 19 | 11 | 8 |
| 占用 SM | 170 | 170 | 156 | 164 | 150 | 132 | 154 | 152 | — | — |

从这张表可以推出 GPC 结构：

- S=9…14 时恒为 11，说明有 11 个 GPC，且每个 GPC 至少有 14 个 SM。
- S=15、16 时为 8，说明其中 8 个 GPC 有 16 个 SM。
- 170 − 8 × 16 = 42 = 3 × 14，所以是 **8 个 16-SM GPC + 3 个 14-SM GPC**。

用它逐行验证：例如 S=3 时 8×⌊16/3⌋ + 3×⌊14/3⌋ = 40 + 12 = 52；S=5 时 8×3 + 3×2 = 30；S=8 时 8×2 + 3×1 = 19。全部吻合。这也与 GB202 完整芯片 12 GPC × 16 SM = 192 SM 的公开规格一致：RTX 5090 屏蔽了 1 个完整 GPC 和 3 个 TPC（每个 TPC 2 个 SM），共 22 个 SM。

由此还能看出：

- **S=2 是唯一不浪费 SM 的簇大小**，因为所有 GPC 的 SM 数都是偶数。
- S=6 和 S=7 的驻留簇数相同，所以 S=7 严格优于 S=6。

### 5.4 调度模型与 S 的选择

S 个 CTA 平分一个 tile 的 key 块。S 太小填不满波次，太大则每个 rank 的工作太少，固定开销（Q 载入、第一块 K/V 无法重叠、簇内合并）占比变高。主机端用下面的代价函数选 S：

$$\text{cost}(S) = \left\lceil \frac{U}{C_S} \right\rceil \cdot \left( \left\lceil \frac{\bar{B}}{S} \right\rceil + \delta \cdot [S>1] \right)$$

- $C_S$ 是上表实测的驻留簇数，启动时每个内核查询一次；
- $\bar{B}$ 是平均每个 tile 的 key 块数（由分块自带的 envelope，即最小/最大可见 key 数算出）；
- $\delta = 2$ 个块是 split 的固定开销；
- 约束：最短的 tile 也要让每个 rank 至少分到 4 个 key 块，否则不切。短上下文时自动退回 S=1，也就是原来的代码路径。

64k 上下文、1024 token 分块时的预测与实测：

| S | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 波次 × 1/S（相对 S=1） | 1 | 0.833 | 0.889 | 0.833 | 0.867 | 1.000 | 0.857 | 0.875 |
| 实测（ms） | 10.81 | **9.08** | 9.66 | 9.14 | 9.52 | 11.02 | 9.50 | 9.77 |
| 实测（相对 S=1） | 1 | 0.840 | 0.894 | 0.846 | 0.881 | 1.019 | 0.879 | 0.904 |

预测与实测的最大偏差是 3.3%（S=8），而且实测的排序与预测完全一致（S=6 甚至比不切还慢，因为它只用了 132 个 SM）。理论下界是 384/170 = 2.26 波；S=2 等效 2.5 波，波次填充率 90.4%。

剩下的 10% 只有换成持久化内核加动态 tile 队列（stream-K）才能拿回，但那需要全局部分和与修补阶段，又回到了工作区的问题。

对 agent 的短增量，同一个代价函数会自动选更大的 S：

| T（64k 历史） | U | 选中的 S | 波次 | SM 填充率 | 原 $\eta$ |
|---:|---:|---:|---:|---:|---:|
| 128 | 48 | 3 | 1 | 92.3% | 28.2% |
| 256 | 96 | 3 | 2 | 92.3% | 56.5% |
| 512 | 192 | 4 | 5 | 93.7% | 56.5% |
| 1024 | 384 | 2 | 5 | 90.4% | 75.3% |

### 5.5 簇内合并协议

key 循环结束后，Q/K/V 的暂存区已经不再需要，直接拿来做合并缓冲（64 行 × 264 列 × 4 B = 67.5 KB，加 64 个 `float2` 的行统计）：

1. 每行的 owner 线程把 $(m_r, \ell_r)$ 写进本 CTA 的共享内存。`cluster.sync()`。
2. 每个线程通过 DSMEM 读所有 rank 的 $(m, \ell)$，算出 $M=\max m_r$、$L=\sum \ell_r e^{m_r-M}$ 和本 rank 的系数 $e^{m_r-M}/L$，把缩放后的 FP32 累加器写回本地共享内存。指数用 `exp2` 加 FMA 预乘 $\log_2 e$ 计算。`cluster.sync()`。
3. rank r 负责输出的第 r 段：按 rank 顺序跨 CTA 读取各 rank 的同一段并求和，写成 BF16。`cluster.sync()`，保证没有 CTA 在别人还读它的共享内存时退出。

共 3 次簇同步，没有全局内存访问。合并的成本被代价函数里的 $\delta$ 覆盖。

## 6. 优化二：不会溢出的 FP16 累加 P·V

### 6.1 动机：抬高上限

§4.4 说明原内核满载时已经用到 FP32 累加峰值的 80%。QK 和 PV 各占一半 FLOPs，如果 PV 改用 FP16 累加（快一倍），张量核心时间变为原来的 3/4，内核的计算上限从 251 提高到

$$\pi_\text{new} = \frac{2}{1/251 + 1/501} = 334\ \text{TFLOP/s}$$

**为什么 QK 不能也用 FP16 累加？** softmax 对 logit 的**绝对误差**敏感：

$$\frac{\partial P_j}{P_j} = \partial x_j$$

logit 的绝对误差会直接变成 P 的相对误差。256 维点积的 logit 可以到几十，FP16 在 32 附近的间距是 2⁻⁵ ≈ 0.03。每次累加的舍入都会直接变成 P 的相对误差，累积下来可达百分之几，这是不可接受的。

P·V 不同：P ∈ [0, 1]，部分和有界。只要处理好**范围**（溢出）和**下溢**（次正规数），FP16 累加的误差远小于 BF16 输出本身的舍入。

### 6.2 溢出：一个可以证明的上界

在每个 64-key 块内，按**本块自己的行最大值** $m_t$ 计算

$$\hat P_j = 2^{-6}\, e^{x_j - m_t}, \quad j \in \text{tile}$$

于是块内最大的 $\hat P$ 恰好是 $2^{-6}$（可以精确表示），64 个之和 $\sum_j \hat P_j \le 64 \times 2^{-6} = 1$。块的部分和 $\mathbf{p} = \sum_j \hat P_j \mathbf{v}_j$ 是 V 各行的**次凸组合**，MMA 链上每个中间结果也都是其中一部分项的和，同样满足

$$\|\mathbf{p}\|_\infty \le (1+\epsilon)\cdot \max_j \|\mathbf{v}_j\|_\infty,\qquad \epsilon \approx 2.5\times10^{-3}$$

其中 $\epsilon$ 来自 P 舍入到 FP16 和链上几次累加舍入的放大。V 缓存本身就是 FP16，$\max|V| \le 65504$。所以只有当 V 缓存已经贴近 FP16 上限（> 6.53×10⁴，这时缓存写入本身就已经饱和）时才可能溢出，**正常数据下不可能溢出**。这个上界与上下文长度、注意力分布都无关。

### 6.3 下溢：为什么必须用块内局部最大值

更简单的做法是用**全局运行最大值** $m$ 代替 $m_t$，这样省掉折回时的一次缩放（实测快 4%）。但 FP16 的最小正规数是 $2^{-14}$，$\hat P_j$ 是正规数的条件是

$$2^{-6} e^{x_j - m} \ge 2^{-14} \iff x_j - m \ge -8\ln 2 \approx -5.55$$

在长上下文里常见的 **attention sink**（某个 token 的 logit 远高于其他所有 token）场景下，全局最大值被 sink 抬高，普通 key 的 $x_j - m$ 常在 −10 以下：

- 在 $e^{-10}$ 处，FP16 次正规数的相对精度只有约 4%；
- 低于 $e^{-13.2}$ 的项（$2^{-6}e^{x}<2^{-25}$）直接舍入成 0。

而这些 key 加起来可能占注意力质量的相当一部分。

改用块内最大值后，每块的最大项都在 $2^{-6}$，块内比它小 $e^{5.55}$ 倍以内的项都是正规数。更小的项即使落进次正规区，每项的绝对误差也不超过 $2^{-25}$，64 项合计相对于块和（≥ $2^{-6}$）不超过 $2^{-13}$，低于 FP16 本身的舍入。块与块之间的量级差异由下一步的 FP32 系数吸收，FP32 要到 $e^{-87}$ 才下溢。

### 6.4 折回 FP32 累加器

块结束时更新运行状态（$m$ 是运行最大值）：

$$m' = \max(m, m_t),\quad \alpha = e^{m - m'},\quad \beta = e^{m_t - m'}$$
$$\mathbf{o} \leftarrow \alpha\,\mathbf{o} + \beta\,\mathbf{p}, \qquad \ell \leftarrow \alpha\,\ell + \beta \sum_j \hat P_j$$

两者都用一条 FMA 完成（`acc = fma(acc, α, β·p)`）。$\ell$ 和 $\mathbf{o}$ 带着同一个 $2^{-6}$ 因子，在最终的 $\mathbf{o}/\ell$ 中约掉，所以不需要额外的反缩放。原来每块一次的 `acc *= α` 循环也合进了这条 FMA。

PV 的计算顺序也调整了：改成 k 维在内层，每 16 个输出列先在两个 FP16 寄存器里累加完 64 个 key，再折回 FP32。

### 6.5 误差预算与实测

- **P 的量化与改前相同**。原内核的 P 也要先转成 FP16 作为 MMA 的输入，所以新增的误差只有 FP16 累加的舍入。
- 每个块的部分和最多经过 4 次累加舍入（64 key / k16）。FP16 的单位舍入是 $u = 2^{-11} \approx 4.9\times10^{-4}$，而输出 BF16 的单位舍入是 $2^{-8} \approx 3.9\times10^{-3}$，前者是后者的 1/8。
- 张量核心内部 k=16 乘积的累加精度和舍入方式由硬件实现决定（公开的测量研究表明它并非严格的 IEEE 逐次舍入）。所以这里只给量级，最终以 FP64 oracle 实测为准。

实测结果：

- NInfer 自带的 611 个 oracle 用例里，相对 L2 误差平均增加 1.5%（BF16 KV：1.562×10⁻³ → 1.586×10⁻³），离判据上限最多 62%（改前 61%）。
- 数值压力测试：64k 上下文，原内核和新内核同时对照 FP64（[`results/numerics_ctx65536.txt`](results/numerics_ctx65536.txt)）：

| 分布 | 把 FP64 精确结果舍入成 BF16 本身的误差（下限） | 原内核 | 新内核（S=1 / 2 / 8） |
|---|---:|---:|---:|
| 均匀 | 1.669e-3 | 1.677e-3 | 1.706e-3 |
| 尖峰（logit 标准差 3） | 1.624e-3 | 1.630e-3 | 1.644–1.647e-3 |
| attention sink | 1.628e-3 | 1.634e-3 | **1.629e-3** |
| V 离群值（\|V\| 到 3×10⁴） | 1.705e-3 | 1.712e-3 | 1.712–1.716e-3 |
| sink + 离群值 | 1.682e-3 | 1.682e-3 | 1.682e-3 |

（相对 L2 误差。）两个内核都贴在 BF16 舍入的下限上，所有分布下都没有非有限值。sink 场景下新内核反而更准：最大误差 7.78e-3，等于舍入下限，而原内核是 8.21e-3。这正是 §6.3 局部最大值设计的效果。

### 6.6 吞吐

单这一项，64k 时 BF16 再快 1.16×，INT8 1.13×，FP8 1.18×。用 §4.4 的模型反推，新内核满载时的单 SM 效率 $R$ 从 200 升到约 230 TFLOP/s：

|---:|---:|---:|---:|---:|
| 128 | 3 | 0.842 | 194.1 | 230.5 |
| 256 | 3 | 0.841 | 194.3 | 231.2 |
| 512 | 4 | 0.894 | 207.0 | 231.6 |
| 1024 | 2 | 0.899 | 208.9 | 232.3 |
| 2048 | 4 | 0.941 | 215.7 | 229.2 |
| 4096 | 2 | 0.947 | 218.3 | 230.6 |

“有效波次效率”已计入 split 的固定开销。改后也是一个常数解释全部 6 个点（±0.7%）。

所以 64k、1024 token 时的 1.40× 可以分解为：波次效率 0.753 → 0.899（×1.19）乘以单 SM 吞吐 200 → 232（×1.16）。

ncu 从另一个角度印证了新上限：32k 上下文、S=2 时，张量管线利用率从 73.8%（FP32 累加 PV）降到 64.3%（FP16 累加 PV），而耗时从 5.20 ms 降到 4.50 ms。按 ncu 锁定的 2.52 GHz 计算，QK 与 PV 在峰值下各需 1.90 ms 和 0.95 ms，合 2.86 ms，2.86 / 4.50 = 63.4%，与 ncu 的 64.3% 一致。利用率“下降”是因为分母（上限）变大了。

## 7. 优化三：BF16 decode 注意力的 K/V 分段载入

decode / MTP 验证用的 BF16 小 T 内核原来是单缓冲：整块 K+V 载入 → 等待 → 计算，计算期间没有在途读请求。按 §1.2 的 Little 定律，这会让 DRAM 在每块计算期间空闲。

改为两段错开：

- K(j) 到达后先发 V(j) 的读，再算 QK(j)；
- V(j) 到达后先发 K(j+1) 的读，再算 PV(j)。

这样始终有一个载入在途，共享内存用量和 grid 都不变。计算顺序完全没变，所以 **611 个用例的误差统计与改前逐位相同**。

64k 时 T=4（MTP3 的验证宽度）200.7 → 190.5 µs（−5%），T=1 188.4 → 184.3 µs（−2%）。整机 MTP3 decode 只快 0.2%：16 层 × 约 10 µs = 0.16 ms，64k 上下文时一轮约 17–20 ms，最多约 0.9%。实测更低，是因为 decode 时注意力内核前后紧挨着权重流内核，DRAM 本来就不空闲。INT8/FP8 的 decode 内核本来就在循环中途预取下一块，不需要改。

### 8.5 功耗墙：整机为什么拿不到内核级的全部收益

64k prefill 期间每 100 ms 采样一次，同时用 nsys 抓一遍完整 prefill（[`results/power_cap_64k_prefill.txt`](results/power_cap_64k_prefill.txt)）：

| | 改前 | 改后 |
|---|---:|---:|
| SM 频率中位数（最低） | 2745 MHz（2550） | **2595 MHz**（2505） |
| 功耗中位数（最高） | 588 W（607） | 600 W（602） |
| 降频原因 | `SW power cap` | `SW power cap` |
| prompt 注意力合计（1024 次调用） | 5683 ms | 4294 ms（**1.32×**） |
| 最后一块每层注意力 | 10.94 ms（与算子基准 11.01 一致） | 8.29 ms（算子基准 7.85） |
| 其余所有内核（一个都没改） | 5778 ms | 5960 ms（**+3.2%**） |
| 整段 prefill | 11499 ms | 10282 ms |

动态功耗 $P \approx \alpha C V^2 f$。卡被功耗墙限住时，固件通过 DVFS 降低电压和频率，把功耗压在 600 W。新内核让张量核心更忙，开关活动因子 α 更大，于是同样的功耗只能换到更低的频率。

定量核对：

- 算子基准里的 1.40× × (2595 / 2745) = **1.32×**，与引擎内实测的注意力提速完全一致。
- 没改的内核慢了 3.2%，小于频率降幅 5.5%，因为其中一部分是访存受限，对 SM 频率不完全敏感。

算子基准每次只跑几十毫秒，碰不到持续功耗墙，所以看不到这个效应。这也是为什么方法学里要求长时间计算受限的测试必须在整机上采样频率和功耗。

**能耗**：588 W × 11.50 s = 6.76 kJ，改后 600 W × 10.28 s = 6.17 kJ。每次 64k prefill 省约 **9%** 的能量。在功耗墙下，真正的指标是每焦耳完成的工作。最后一波空转的 SM 也有静态功耗，所以填满波次本身就能提高能效。

## 10. 否决的方案和原因

| 方案 | 实测 | 原因分析 |
|---|---|---|
| 每 CTA 8 个 warp、128 行 × 32 key，让每个调度器有 2 个 warp 互相掩盖 | 与现在的 4 warp × 64×64 持平（8.64 对 8.52 ms） | 同一 CTA 内的 warp 在每块边界都要同步，各 warp 齐步走，softmax 仍然不与 MMA 重叠。要重叠必须做 FA3 式的显式乒乓调度，让两组 warp 错开半个相位 |
| PV 的 FP16 累加链交错 2/4 组 n-tile | +1.6%，但溢出 32 B 到栈上 | 寄存器已经 254/255，更多独立累加链只能靠溢出换取 |
| β 折回改用 FP16 `HMUL2` | +0.4% | 多一次 FP16 舍入，把 §6.5 的误差预算换来不到 1% 的速度 |
| 用全局最大值 × 2⁻⁶ 的 FP16 累加 | +4% | attention sink 场景下小 P 落进次正规区（§6.3） |
| INT8/FP8 decode 内核做同样的 K/V 分段载入 | — | 它们本来就在循环中途预取下一块 |
| GEMV 的寄存器预取队列、L2 预取 | 持平或更慢 | 已在带宽上限，见 §3.3 |
| 用 cuTile Rust / cuda-oxide 重构整个引擎 | — | 不改变任何一个上限（§3.4） |

## 11. 剩余空间

用同样的模型可以给出每一项剩余空间的上限：

1. **BF16 prompt 注意力**：新的计算上限是 334 TFLOP/s，满载时 $R$ ≈ 230，约 69%。剩下的主要是单 warp/SMSP 下 softmax 与等待无法被掩盖。
   - 按编程指南的 MUFU 吞吐（每 SM 每周期 16 个 `ex2`）估算，每个 64×64 块的 exp 和归约约占 MMA 时间的 10–15%，加上每块的同步与载入等待，与观察到的约 30% 量级相符。这一条是估算。
   - 要再往上，需要 FA3 式的 warp 乒乓：两组 warp 交替做 softmax 和 MMA。在 99 KB 共享内存和 D=256 下，这需要重新设计 tile 形状。
   - 若达到 85%（284 TFLOP/s），64k prefill 的注意力还能再快 1.23×（估算）。
2. **INT8 prompt 注意力**：上限是 QK 用 INT8、PV 用 FP16 累加的调和平均 667 TOP/s，现在只有 197，约 30%。瓶颈是生产者（QK）、反量化、消费者（PV）三段被屏障串行。要让 QK(j+1) 与 PV(j) 重叠，需要加倍 V 的 FP16 暂存，会超出 99 KB，属于重写。按张量核心时间算还有约 2× 空间。做成之后，INT8 KV 在显存减半的同时 prefill 也会比 BF16 快。
3. **decode T=1 注意力**：离 1.70 TB/s 还差约 13%，另有每层 5 µs 的独立合并内核可以融合。
4. **功耗墙**：只要长 prefill 仍然顶着 600 W，任何让张量核心更忙的优化，在整机上都要打约 5% 的折扣。从这个角度看，减少无效工作（空转的 SM、冗余的数据搬运）比单纯提高单 SM 吞吐更划算。

## 12. 结论

1. **decode 是 DRAM 带宽问题，而且已经解决到 87%。** 实测上限 1.70 TB/s，两条独立的读路径都收敛到这个值。剩下的差距里，最大的一项根因是冷取指而不是访存，修掉后整机 +1.25%、输出逐位不变。继续投入的边际收益是个位数百分比。要大幅提速，只能减少每 token 的字节数，或者每读一遍权重产出更多 token。
2. **超长上下文 prefill 是计算问题，损失可以精确分解。** 原内核的 60% 效率等于 75.3% 的波次效率乘以 80% 的单 SM 效率，6 个形状只用一个参数就拟合到 ±0.7%。前者用 cluster split-KV 解决：利用在线 softmax 的幺半群结构在片上合并，不需要工作区，簇大小由实测的 GPC 拓扑和代价函数选出。后者通过把 PV 换到 FP16 累加来抬高上限：块内局部最大值加 2⁻⁶ 缩放，可以证明不会溢出，也避开了次正规区。
3. **agent 场景受益最大。** 在混合架构模型上，长历史 agent 单轮的代价几乎全在 16 层注意力的“短查询 × 长 key”形状上，原内核在这里只用了 28–56% 的 SM。改后这部分注意力快 1.7–3.4×，整机单轮的到首 token 时间快 1.2–1.56×。
4. **整机要对着功耗墙看。** 600 W 墙让内核级 1.40× 变成引擎内 1.32×，降频幅度精确解释了这个差值；同时每次 prefill 省约 9% 的能量。
